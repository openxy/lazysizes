# 平台收编：原生 loading=lazy

## 本版本引入的概念

**平台吸收（平台吃掉库）**：2020 年前后浏览器原生支持 `loading="lazy"`——HTML 属性一行，做了这个库七百行代码做的事：

```html
<img src="图.jpg" loading="lazy" alt="">
```

且由浏览器引擎在更底层实现：不占页面 JS 主线程、有自己的调度优先级、无需任何扫描。库的核心价值被平台整体拿走。5.3.1 是这个项目的最后一个 tag——维护期收官，恰是「库被平台收编」的标准结局。

**过渡形态（bridge）**：本版真正值得读的代码是 `plugins/native-loading/ls.native-loading.js`——它不是又一个功能插件，而是**库向平台的让位协议**：检测到浏览器支持时，把库自己的事件监听全拆掉，揭幕改设原生属性，退化为原生机制的薄壳。一个库体面退场的样子，都写在这 140 行里（见文件级解读）。

## 弧线收束（整个案例集的终点）

| 阶段 | 上游线 | 库在干什么 |
|---|---|---|
| v1 系列（1.x，2015） | scroll 轮询 | 手写实现：事件 + 节流 + 全量扫描 |
| v4 系列（4.x，2017） | 调度成熟 | rIC/rAF/防抖转正；IO 版停在 src/ 实验位 |
| v5 系列（5.x，2018-19） | 维护期 | 平台收编：native-loading 插件让位，主线只做兼容修补 |

一条完整的技术普及弧线：**手写实现 → 库繁荣（生态、调度、兼容面）→ 平台原生 → 库退役**。注意中间那步「IO 实验未转正」：等浏览器把 IntersectionObserver 补齐的时候，平台顺手把懒加载整个做掉了——实验变体永远停在了 src 目录。

## 什么信号说明一个库会被平台吸收

- 能力单一且边界清晰（「图片进视口才加载」一句话说得完）；
- 需求普遍到浏览器厂商有动力标准化（省流量是全网诉求）；
- 库本身在教浏览器怎么做（lazysizes 们的实践证明了调度策略，平台照着抄）。

对照反例：React 这类复杂视图框架能力边界模糊、争议多，短期内看不到吸收路径。你选依赖时可以拿这三条掂量：**越接近「会被吸收」的能力，越要写得容易被替换**。

## 怎么学这个版本

1. 精读 `doc/plugins/native-loading/ls.native-loading.js.md`（让位协议的完整逻辑）；
2. `lazysizes.js` 与 v4 系列同构，**略读即可**——维护期的改动只剩工程修补（SSR 场景安全传 window、AMD 注册、`ls-is-cached` 缓存标记类、iframeLoadMode 配置），「不再变」本身就是成熟期的意义；
3. 浏览 `plugins/` 目录（二十多个）——生态全貌是繁荣期的化石层。

## 思考题

- 今天（2026 年）新建页面还需要懒加载库吗？什么场景仍要？（提示：`data-sizes="auto"` 这类**自动算显示宽度**的能力，平台至今没给；需精细控制预载距离的产品也一样）
- `loading="lazy"` 与 IntersectionObserver 是什么关系？（前者是产品化的浏览器功能，后者的观察机制是它可用的底层手段之一——平台上叠平台）
- native-loading 插件为什么保留 data-src 标记、不直接劝用户改写原生属性？（一套标记吃所有浏览器——渐进增强的立场选择）
