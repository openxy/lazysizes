# 原生 loading 插件

## 本版本引入的概念

**平台吸收（平台吃掉库）**：浏览器原生支持 `loading="lazy"`——HTML 一行属性，做了这个库七百行代码做的事：

```html
<img src="图.jpg" loading="lazy" alt="">
```

且由引擎在更底层实现：不占页面 JS 主线程、自带调度优先级、无需任何扫描。库的核心价值被平台整体拿走。这是 5.x 里程碑的起点：库从「提供懒加载」转向「与原生共存直至让位」。

**过渡形态（bridge）**：本版真正值得读的是 `plugins/native-loading/ls.native-loading.js`——不是功能插件，是**库向平台的让位协议**：检测到浏览器支持时，把库自己的事件监听全拆掉（polling 案例里那张宽事件面的彻底退场），揭幕改设原生属性，`prematureUnveil` 钩子对支持原生的元素返回「不归你加载」。一个库体面退场的样子，都写在这 140 行里（见文件级解读）。

**同期硬话**：5.0.0 还把 `width`/`height` 内容属性用作宽高比探测、堵了全局 `lazySizesConfig` 泄漏——为「原生属性 + 库辅助」的混搭时代做铺垫。

## 本版本的改动（差异面板对照上一版 mature/refined）

跨案例对照（4.1.0 → 5.0.0）：主文件机制几乎不动（约 98 行），新增 plugins/native-loading/；`lowRuns` 初值、expand 档位微调。**架构不动的本身就是信息**：库已进入只修不长的阶段。

## 什么信号说明一个库会被平台吸收

- 能力单一、边界清晰（「进视口才加载」一句话说得完）；
- 需求普遍到浏览器厂商有动力标准化（省流量是全网诉求）；
- 库的实践证明了调度策略可行——平台照着抄。

对照反例：React 这类视图框架能力边界模糊、做法争议多，短期看不到吸收路径。选依赖时拿这三条掂量：**越接近「会被吸收」的能力，越要写得容易被替换**——lazysizes 的标记语言（data-src）后来被原生属性无缝接管，就是「容易被替换」的正面教材。

## 思考题

- native-loading 插件为什么保留 data-src 标记、不直接劝用户改写原生属性？（一套标记吃所有浏览器——渐进增强的立场）
- `loading="lazy"` 与 IntersectionObserver 是什么关系？（前者是产品化的浏览器功能，后者的观察机制是它可用的底层手段——平台上叠平台）
- 若你在 2019 年选型：原生属性已在 Chrome 落地、Safari 还没有，你的页面标记怎么写才能两头都不坏？
